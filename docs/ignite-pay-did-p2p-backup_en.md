To establish a DID-based mutual trust connection between the MCP Server and the mobile app, the core task is to implement a **"bidirectional asynchronous identity verification and encrypted channel negotiation"** process. Since the MCP Server typically runs as a persistent service and the mobile app acts as the controller, their interaction can be modeled on a simplified version of the **DIDComm** protocol.

**"Client-Side: Multi-Device DID Identity Mutual Trust and Connection Guide"**

---

### 1. Core Logic: From "Identity Binding" to "Secure Handshake"

Do not attempt to share a single set of private keys across multiple devices. The correct approach is: **each endpoint holds its own independent key pair, authorized and linked through the user's Root DID.**

* **Root DID**: The user's root identity (typically corresponding to the Solana wallet).
* **Mobile DID/Key**: A local temporary identity generated by the mobile App.
* **Server DID/Key**: A local service identity generated by the MCP Server.

---

### 2. Connection Establishment Flow (Three Phases)

#### Phase 1: Discovery and Handshake Initiation (Discovery)
The MCP Server typically provides the connection entry point.
1.  **Server generates invitation**: The MCP Server generates a QR code containing its **Server DID** and **Service Endpoint** (such as an IP address or domain name).
2.  **Mobile scans QR code**: The user opens the App and scans the QR code to obtain the Server's identity information.

#### Phase 2: Mutual Authentication (Mutual Authentication)
This is the key to establishing trust — both parties must prove "we serve the same owner."
1.  **Credential exchange**: Both parties exchange their respective **Delegate VCs** (authorization credentials issued by the user's Root DID).
    * *App credential content*: "Root DID authorizes $PK_{mobile}$ to act on my behalf."
    * *Server credential content*: "Root DID authorizes $PK_{server}$ to act on my behalf."
2.  **On-chain / local verification**:
    * The App checks the Server's credential, confirming that its Subject is indeed the same Root DID and that it is in an "authorized" state within the ZK compression state tree.
    * The Server performs the same check.

#### Phase 3: Encrypted Channel Establishment (Encryption)
1.  **Key exchange**: Both parties use their respective ephemeral public keys to negotiate a symmetric encryption key via the **Diffie-Hellman (ECDH)** algorithm.
2.  **Channel encryption**: All subsequent MCP commands (such as reading files or sending payment requests) are transmitted through this encrypted channel, ensuring that third parties cannot eavesdrop.

---

### 3. Development Implementation Guide (Implementation)

#### 3.1 Mobile Side (App Side)
* **Key management**: Use the phone's secure enclave (e.g., iOS Secure Enclave) to store $PK_{mobile}$.
* **Authorization request**: On first connection, invoke the user's Solana wallet (e.g., Phantom) to sign the MCP's public key, generating an authorization VC.

#### 3.2 Server Side (MCP Server Side)
* **Identity persistence**: The Server generates its own DID upon initialization.
* **Permission validation filter**: Before processing an MCP Protocol `call_tool` or `read_resource` request, the request source's `Signer` must first be verified against the authorization list.

#### 3.3 Storage Structure (ZK Compression Perspective)
It is recommended to maintain an **endpoint list** within the user's compressed account:

```rust
pub struct Endpoint {
    pub pubkey: Pubkey,      // Public key of the endpoint (mobile or server)
    pub name: String,        // Alias, e.g. "iPhone 15" or "Home_Server"
    pub status: u8,          // Status: 1=activated, 0=revoked
}
```

---

### 4. Security Scenario Responses

| Scenario | Solution |
| :--- | :--- |
| **Phone lost** | The user uses the Root wallet to send an on-chain `revoke_endpoint` instruction, revoking the phone's $PK_{mobile}$. The MCP Server detects the revocation and automatically disconnects. |
| **Changing MCP environment** | Repeat the "scan-authorize-bind" flow. Since the Root DID remains unchanged, all historical data and VCs can be seamlessly migrated. |
| **Man-in-the-middle attack** | Through bidirectional VC verification and ECDH key exchange, even if an attacker intercepts the QR code, they cannot forge the authorization signature from the Root DID. |

```json
{
  "method": "did_connect",
  "params": {
    "requester_did": "did:sol:app_address",

  }

```

**Summary:**
This scheme enables the MCP Server and the mobile App to form a **"one core (Root DID), multiple endpoints (Delegates)"** mesh trust structure. This design ensures that a single-point leak does not compromise the entire system, while also enabling seamless cross-device collaboration.
