# Ignite Pay — 黑客松项目陈述

> **核心定位：基于 x402 协议的 M2M（Machine-to-Machine）支付基础设施 + 手机用户实时授权**

---

## 一、新颖性 (Novelty)

### 1.1 x402 协议 + MCP 工具链：Agent 碰到付费墙自动发起支付

传统支付是"人主动发起"——打开钱包 App、扫码、确认。Ignite Pay 反转了这个模式：

- AI Agent 在执行任务时遇到 HTTP 402 付费墙，自动解析 `PaymentRequirements`，通过 MCP 工具发起支付流程
- MCP（Model Context Protocol）工具链提供 39 个标准化工具（买家 23 个 + 商户 16 个），任何兼容 MCP 的 AI 客户端（Claude、Cursor 等）即插即用
- 整个过程无需人工干预——**机器发起、人授权**，这是与代币转账的本质区别

```
传统支付：人 → 打开 App → 扫码 → 确认 → 链上转账
Ignite Pay：Agent → 遇到 402 → MCP 解析 → 风控检查 → [自动|手机授权] → 链上支付
```

### 1.2 DIDComm v2 端到端加密：机器到人的授权通信全程加密

Agent 到手机的支付授权通信走 DIDComm v2 协议：

- **JWE Authcrypt 加密**：基于 X25519 密钥协商，中继服务器只能看到密文，无法读取支付金额、商户信息
- **Ed25519 签名**：每条消息附带发送方签名，防止伪造
- **去中心化身份**：使用 `did:ignite:z6Mk...` 格式的 DID 标识符，基于 Ed25519 多基数编码
- 中继服务器（Mediator）完全零知识——即使被攻破，攻击者也无法读取用户支付指令

### 1.3 六层风控体系：从黑名单到白名单的全覆盖

不是简单的"允许/拒绝"二元决策，而是六层渐进式风控：

| 层级 | 规则 | 动作 |
|------|------|------|
| L1 | 商户黑名单 | 直接拒绝 |
| L2 | IPFS CID 黑名单 | 内容级别拒绝 |
| L3 | 单笔金额限额 | 超额需授权 |
| L4 | 白名单自动通过 | 信任商户 + 额度内自动批准 |
| L5 | IPFS CID 白名单 | 信任内容源自动批准 |
| L6 | 默认推手机 | 不在任何名单 → 手机授权 |

这意味着用户可以安全地让 Agent 自主处理小额支付（L4 白名单 / L3 限额内），同时在风险较高时保留人类的实时审核权。

### 1.4 MagicBlock 链下 Voucher + Sum-Merkle 批量结算

MagicBlock 支付通道是一个完整实现的第四条支付路径：

- **链下 Voucher 签名**：用户在手机上授权后，MCP 签名一个 Ed25519 Voucher（`SHA256(channel_id ‖ seq ‖ amount)`），延迟 <50ms
- **三层架构**：L1 Solana 结算层 → MagicBlock Execution Reality（确定性执行环境）→ 链下服务
- **Sum-Merkle Tree 批量结算**：数千笔链下支付压缩成一笔链上交易，极大降低链上负载
- **争议机制**：买家可通过 `dispute` → `resolve_dispute` 提交欺诈证明（基于 Sum-Merkle 树），链上仲裁
- **链上程序**：MagicBlock 是 3 个已部署的 Solana 程序之一，11 条指令，完整的状态机管理

### 1.5 与传统代币转账的本质区别

| 维度 | 传统代币转账 | Ignite Pay |
|------|-------------|-----------|
| 发起方 | 人 | AI Agent（MCP 工具） |
| 授权方式 | 私钥签名 | DIDComm 加密推送 + 手机滑动确认 |
| 身份验证 | 地址字符串 | 链上 DID + Verifiable Credential |
| 风控 | 无 | 六层渐进式风控 |
| 隐私 | 公开地址 | 中继零知识（JWE 加密） |
| 高频支付 | Gas 成本高 | MagicBlock 链下 Voucher <50ms |

## 二、潜在影响 (Potential Impact)

### 2.1 M2M 支付：下一个万亿级市场

**机器到机器（M2M）支付是一个即将爆发的巨大市场。** 随着 AI Agent、IoT 设备、自动驾驶的普及，机器之间自主完成交易的需求正在指数级增长：

- **AI Agent 爆发**：Gartner 预测到 2028 年，33% 的软件交互将由 AI Agent 完成。每个 Agent 执行任务时需要访问付费 API、数据源、算力——每次访问都是一笔 M2M 支付
- **IoT 设备互联**：全球 IoT 设备数量预计 2030 年将超过 290 亿台。充电桩自动结算、带宽按需购买、传感器数据付费——都需要机器自主支付
- **自主经济代理（AEA）**：Fetch.ai 等项目已经证明，机器之间的自主协商和支付是可行的。但缺乏一个统一的支付协议和安全的授权机制
- **传统支付的盲区**：现有的支付基础设施（信用卡、PayPal、甚至链上钱包）全部是为"人主动发起"设计的。没有一个支付方案原生支持"机器发起、人授权"的 M2M 模式

**核心洞察：谁先解决 M2M 支付的信任和授权问题，谁就占据了 Agent 经济的基础设施层。**

Ignite Pay 的回答：
- **x402 协议**：标准化的机器支付挑战格式，Agent 遇到 402 自动处理
- **DIDComm 授权**：机器发起的支付请求通过加密通道推送到人的手机，人一划确认
- **渐进式风控**：小额自动通过、大额推手机、黑名单直接拒绝——机器自主性与人类控制权的完美平衡
- **MagicBlock 亚秒级结算**：M2M 场景对延迟敏感，链下 Voucher <50ms 满足高频需求

### 2.2 Solana 生态契合点

Solana 的技术特性与 M2M 支付场景高度契合：

Solana 的技术特性与 Agent 支付场景高度契合：

| Solana 特性 | Agent 支付需求 |
|-------------|---------------|
| ~400ms 确认延迟 | Agent 需要快速确认以继续任务 |
| 低 Gas 费用 | 微支付场景对成本敏感 |
| PDA（程序派生地址） | 天然适合 DID 身份管理 |
| MagicBlock Execution Reality | 链下确定性执行 + 亚秒级结算 |
| SPL Token 标准 | 原生支持多资产支付 |

### 2.3 场景延展：从 Agent 支付到消费者扫码微支付

Ignite Pay 的支付引擎不仅服务于 Agent，还延展到消费者场景：

- **消费者扫码支付**：商户 App 生成支付二维码，消费者 App 扫码确认
- **自动售货机**：MagicBlock <50ms 支付，适合无人设备
- **内容付费**：Agent 遇到付费墙自动支付，消费者浏览付费文章同样适用
- **IoT 设备结算**：设备间自动微支付（充电桩、带宽共享等）

### 2.4 对 Solana 生态的长期贡献

- **DID 标准落地**：为 Solana 生态提供了一套完整的去中心化身份方案
- **MCP 支付标准**：定义了 AI Agent 通过 MCP 协议进行支付的标准化接口
- **x402 在 Solana 的实现**：将 Coinbase 的 x402 协议从 EVM 扩展到 Solana 生态

## 三、用户体验 (UX)

### 3.1 双层支付速度

| 支付路径 | 延迟 | 适用场景 |
|---------|------|---------|
| MagicBlock 链下 Voucher | <50ms | 高频微支付、API 按调用计费 |
| Session Key 链上支付 | ~400ms | 标准链上 SOL/SPL 转账 |
| Direct Wallet Deep Link | ~400ms | 用户选择外部钱包签名 |
| Relayer 代付 | ~400ms | 零 Gas 门槛用户引导 |
| CCTP 跨链 USDC | 10-30min | EVM 链 USDC 充值到 Solana |

多路径支付引擎根据场景自动选择最优路径：
- 存在 MagicBlock 通道 → 链下 Voucher（最快）
- 小额 + 白名单 → 自动通过 Session Key（零用户交互）
- 大额 / 新商户 → 推送手机授权
- 用户无 Solana 钱包 → Relayer 代付
- 用户只有 EVM 链资产 → CCTP 跨链充值

### 3.2 手机一划确认的交互设计

当支付需要用户授权时：

1. **推送通知**：手机 Dashboard 出现 amber 横幅 "Payment authorization requested"
2. **点击授权**：ChallengeScreen 弹窗显示商户 DID、支付金额、描述信息
3. **滑动确认**：滑到 85% 以上触发签名
4. **选择签名方式**：内置密钥（Session Key）/ 外部钱包（Phantom、Solflare）
5. **自动关闭**：确认后 1.2 秒弹窗自动关闭

关键设计决策：
- 所有通信通过 DIDComm v2 加密，中继服务器无法读取内容
- Session Key 是临时密钥，有独立的消费限额和有效期，即使泄露也不影响主钱包
- 弹窗提供三种操作：本次授权 / 加入白名单 / 加入黑名单

### 3.3 全 Rust 后端 + Flutter 移动端

| 层级 | 技术选型 | 理由 |
|------|---------|------|
| 链上程序 | Anchor (Rust) | Solana 原生开发框架 |
| 后端服务 | Axum 0.8 + tokio | 高性能异步 Rust |
| 持久化 | sled | 嵌入式数据库，零部署 |
| 移动端 | Flutter + Rust Bridge | 共享加密逻辑，跨平台 |
| MCP 服务 | Rust (rmcp) | 类型安全的工具定义 |
| 基础设施 | Docker Compose + nginx | 一键部署 |

两个完整的移动端 App：
- **买家 App**（`ignite_pay_app`）：消费者使用，包含 DID 创建、Mediator 连接、配对、支付授权
- **商户 App**（`ignite_pay_merchant_app`）：商户使用，管理收款、查看订单

### 3.4 完整的开发者体验

- **一键启动**：`make init && make build && make up` 启动全部后端服务
- **健康检查**：`make health` 验证所有服务状态
- **MCP 即插即用**：配置 `config.toml` 后直接运行，兼容 Claude Desktop / Cursor
- **端到端测试指南**：`docs/agent-payment-e2e-test-guide.md` 覆盖 5 条支付路径

## 四、商业计划 (Business Plan)

### 4.1 M2M 支付的巨大市场机会

Ignite Pay 切入的是一个指数级增长的市场空白：

| 趋势 | 数据 | 对 M2M 支付的影响 |
|------|------|-------------------|
| AI Agent 增长 | 2028 年 33% 软件交互由 Agent 完成 | 每个 Agent 每次调用付费 API 都需要 M2M 支付 |
| IoT 设备增长 | 2030 年全球超 290 亿台 | 设备间自主结算（充电、带宽、数据）需要 M2M 支付 |
| API 经济 | 全球 API 市场 2030 年预计超 $4000 亿 | 按调用计费的 API 是 M2M 支付的最大场景 |
| 自主经济代理 | Fetch.ai / Olas 等生态快速增长 | AEA 之间的自主交易需要标准化的支付协议 |

**为什么是现在？**
- x402 协议刚刚发布（Coinbase 2024），Agent 支付有了标准化格式
- MCP 协议被广泛采用（Anthropic 2024），Agent 工具调用有了统一接口
- MagicBlock 在 Solana 上提供确定性执行环境，链下 Voucher 结算成为可能
- **三者在 2024-2025 年同时成熟，M2M 支付的基础设施条件首次具备**

**Ignite Pay 的市场定位：**
- 不是做"又一个支付 App"——而是做 **Agent 经济的支付协议层**
- 不是做"又一个链上钱包"——而是做 **M2M 支付的授权和风控基础设施**
- 类比：Visa 是人类支付的信用卡网络 → Ignite Pay 是机器支付的授权网络
